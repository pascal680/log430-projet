SECTION 1 - ANALYSE METIER ET DDD
================================================================================

1.1 Description du systeme et contexte
----------------------------------------

CanBankX est une plateforme bancaire numerique construite en microservices,
destinee aux investisseurs particuliers. Le systeme permet a des clients de
s'inscrire, de s'authentifier avec un second facteur, d'ouvrir des comptes
bancaires et de realiser des virements avec garantie de non-doublement.

Le projet est divise en trois bounded contexts DDD, chacun materialise par un
microservice Spring Boot independant, exposes via une API Gateway unique
(KrakenD). En mode production avec load balancing, Nginx distribue le trafic
sur deux instances de chaque service.

Les clients interagissent uniquement via KrakenD sur le port 8080. Prometheus
collecte les metriques de chaque service toutes les 15 secondes et Grafana
les visualise dans un dashboard auto-provisionne.


1.2 Glossaire du domaine
--------------------------

Client          : Personne physique inscrite sur la plateforme. Cycle de vie :
                  PENDING -> ACTIVE -> SUSPENDED.

NAS             : Numero d'assurance sociale, identifiant unique par client.
                  Contrainte UNIQUE en base de donnees.

OTP             : One-Time Password (code a 6 chiffres). Envoye par email lors
                  de l'inscription (verification KYC) et lors du login MFA.

Challenge Token : Jeton temporaire emis entre les etapes "login" et "MFA".
                  Stocke dans Redis avec un TTL de 5 minutes.

Account         : Compte bancaire appartenant a un client. Types : CHECKING
                  (cheque) ou SAVINGS (epargne). Identifie par un
                  accountNumber genere.

BankTransaction : Mouvement financier de type DEBIT, CREDIT ou TRANSFER.
                  Possede une cle d'idempotence (idempotencyKey) stockee en
                  Redis (24h TTL) et en base avec contrainte UNIQUE.

AuditLog        : Journal d'evenements append-only trace par le payment-service
                  pour chaque etape d'une transaction. Ne peut jamais etre
                  modifie ou supprime.

Idempotency-Key : Header HTTP fourni par le client lors d'une requete de
                  paiement. Garantit qu'un reseau instable ne provoque pas de
                  doublon de debit.

Bounded Context : Perimetre fonctionnel coherent du DDD. Chaque bounded context
                  a son propre modele, son propre schema MySQL et son propre
                  service Spring Boot.


1.3 Cas d'utilisation (UC-01 a UC-05)
---------------------------------------

Les cinq cas d'utilisation couvrent le parcours complet d'un client, de
l'inscription au premier virement bancaire. Tous sont implementes de bout en
bout et valides par le smoke test k6.


UC-01 : Inscription et verification KYC
.........................................

Acteur principal  : Client (futur)
Service principal : identity-service
Precondition      : Aucune

Description :
  Le client soumet ses informations personnelles (prenom, nom, email, mot de
  passe, NAS, telephone, adresse). Le systeme cree un compte avec le statut
  PENDING et envoie un code OTP a 6 chiffres a l'adresse email fournie. Le
  client soumet le code OTP via POST /api/clients/{id}/verify pour que son
  compte passe a ACTIVE. Pour les tests automatises, un administrateur peut
  activer directement le compte via POST /api/clients/{id}/activate (bypass OTP).

Resultat attendu  : Compte ACTIVE cree, client peut s'authentifier.

Regles metier :
  - L'email doit etre unique (contrainte UNIQUE en base).
  - Le NAS doit etre unique et avoir exactement 9 chiffres.
  - Le mot de passe est hache avec BCrypt force 8 avant persistance.
  - L'OTP expire automatiquement (Redis TTL).

Codes HTTP :
  201 Created      - inscription reussie
  409 Conflict     - email ou NAS deja utilise
  400 Bad Request  - champs manquants ou invalides


UC-02 : Authentification a deux facteurs (MFA)
...............................................

Acteur principal  : Client
Service principal : identity-service
Precondition      : Compte client ACTIVE (UC-01 complete)

Description :
  Etape 1 - Le client envoie ses identifiants (email + mot de passe) via
  POST /api/auth/login. Le systeme valide les credentials avec BCrypt,
  genere un challenge token unique et l'enregistre dans Redis (TTL 5 min),
  puis envoie un code OTP par email. La reponse contient uniquement le
  challengeToken.

  Etape 2 - Le client soumet le challengeToken et le code OTP via
  POST /api/auth/mfa. Le systeme verifie le token dans Redis et valide
  l'OTP. En cas de succes, la session est consideree etablie (stateless :
  le client doit rejoindre son token de session a chaque requete).

Resultat attendu  : 200 SUCCESS, le client est authentifie.

Codes HTTP :
  200 OK           - MFA valide, session etablie
  401 Unauthorized - credentials invalides ou token expire
  400 Bad Request  - champs manquants


UC-03 : Ouverture d'un compte bancaire
.......................................

Acteur principal  : Client
Service principal : account-service
Precondition      : Compte client ACTIVE

Description :
  Le client choisit le type de compte (CHECKING ou SAVINGS) et fournit un
  solde initial optionnel via POST /api/accounts. Le systeme genere un
  numero de compte unique (accountNumber) et persiste le compte en base.

Resultat attendu  : Compte cree avec son accountNumber, type et solde initial.

Codes HTTP :
  201 Created      - compte ouvert
  404 Not Found    - clientId inexistant


UC-04 : Consultation du solde et de l'historique des transactions
.................................................................

Acteur principal  : Client
Service principal : account-service + payment-service (agreges par KrakenD)
Precondition      : Au moins un compte ouvert (UC-03 complete)

Description :
  Le client consulte son solde et ses dernieres transactions via
  GET /api/accounts/{accountNumber}/summary. KrakenD execute deux appels
  en parallele : un vers account-service pour le solde et les details du
  compte, et un vers payment-service pour les transactions recentes. Les
  deux reponses sont fusionnees en un seul objet JSON avec des groupes
  nommes ("account" et "recentTransactions").

Resultat attendu  : Solde actuel et liste des transactions dans une seule reponse.

Codes HTTP :
  200 OK           - donnees retournees
  404 Not Found    - compte inexistant


UC-05 : Virement bancaire avec garantie exactly-once
.....................................................

Acteur principal  : Client
Service principal : payment-service (orchestrateur)
Precondition      : Deux comptes existants, solde suffisant sur le compte source

Description :
  Le client soumet une transaction via POST /api/transactions avec un header
  Idempotency-Key unique. Le payment-service :
    1. Verifie si la cle existe dans Redis (hit = doublon, retourne la
       meme reponse sans re-executer).
    2. Si miss Redis, verifie en base de donnees (fallback).
    3. Cree la transaction en PENDING en base.
    4. Appelle account-service pour debiter le compte source.
    5. Pour un TRANSFER, appelle account-service pour crediter le
       compte destination.
    6. Met a jour la transaction en COMPLETED.
    7. Enregistre la cle dans Redis (TTL 24h).
    8. Envoie un email de confirmation de facon asynchrone.

  En cas d'echec du credit (etape 5), un CREDIT de compensation est
  emis pour restaurer le solde du compte source et la transaction passe
  a FAILED. Chaque etape est tracee dans l'AuditLog.

Resultat attendu  : Transaction COMPLETED, soldes mis a jour, email envoye.

Codes HTTP :
  201 Created      - transaction reussie
  422 Unprocessable Entity - solde insuffisant
  404 Not Found    - compte source ou destination inexistant


1.4 Modele de domaine (Bounded Contexts)
------------------------------------------

Trois bounded contexts DDD, chacun isole dans son service et son schema MySQL.
Les references cross-service se font uniquement par identifiants metier.

Bounded Context : Identite (identity-service / db_identity)
  Entite racine : Client
    - id            : UUID (cle primaire)
    - firstName     : String
    - lastName      : String
    - email         : String (UNIQUE)
    - passwordHash  : String (BCrypt)
    - nas           : String (UNIQUE, 9 chiffres)
    - phoneNumber   : String
    - address       : String
    - status        : Enum {PENDING, ACTIVE, SUSPENDED}

Bounded Context : Comptes (account-service / db_account)
  Entite racine : Account
    - id            : UUID (cle primaire)
    - accountNumber : String (UNIQUE, genere)
    - clientId      : UUID (reference vers identity-service, pas de FK cross-service)
    - type          : Enum {CHECKING, SAVINGS}
    - balance       : BigDecimal
    - createdAt     : LocalDateTime

Bounded Context : Paiements (payment-service / db_payment)
  Entite racine : BankTransaction
    - id               : UUID (cle primaire)
    - idempotencyKey   : String (UNIQUE, contrainte DB + cache Redis)
    - sourceAccountNumber : String
    - targetAccountNumber : String (optionnel, TRANSFER uniquement)
    - amount           : BigDecimal
    - type             : Enum {DEBIT, CREDIT, TRANSFER}
    - status           : Enum {PENDING, COMPLETED, FAILED}
    - createdAt        : LocalDateTime

  Entite : AuditLog (append-only)
    - id            : UUID (cle primaire)
    - transactionId : UUID (reference vers BankTransaction)
    - action        : String
    - details       : String
    - createdAt     : LocalDateTime

SECTION 2 - ARCHITECTURE ET DECISIONS

2.1 Vue d'ensemble (Arc42 - sections 1 a 8)
---------------------------------------------

CanBankX est une architecture microservices orchestree par une API Gateway.
L'approche retenue decompose le domaine bancaire en trois services independants,
chacun avec sa propre base de donnees (schema isole), son propre cycle de
deploiement et ses propres metriques d'observabilite.

Objectifs de qualite (par ordre de priorite) :
  1. Exactitude    - Aucun doublon de paiement, meme en cas de retry reseau.
                     Mesure : idempotency key + smoke test (meme txId retourne).
  2. Performance   - p95 < 400 ms (lectures), < 1500 ms (transactions) a 50 VUs.
                     Mesure : load test k6.
  3. Disponibilite - Les 3 services repondent a /actuator/health en permanence.
                     Mesure : smoke test (healthchecks).
  4. Observabilite - 4 Golden Signals visibles en temps reel dans Grafana.
                     Mesure : dashboard auto-provisionne.
  5. Securite      - Mots de passe haches, sessions stateless, reseau isole.
                     Mesure : BCrypt 8 + Spring Security.

Parties prenantes :
  Client bancaire  : Virements fiables depuis n'importe quel client HTTP.
  Developpeur      : Swagger UI par service, collection Postman complete.
  Ops              : Dashboard Grafana avec 4 Golden Signals, JVM, HikariCP.
  Correcteur LOG430: Architecture documentee, charge testee, decisions justifiees.


2.2 Contraintes architecturales
---------------------------------

  Spring Boot 3 / Java 21   : Framework impose. JPA/Hibernate pour la persistance.
  MySQL 8.4                 : Base de donnees relationnelle (3 schemas isoles).
  Runtime Docker            : Tout tourne en conteneurs, orchestres par Compose.
  Stateless                 : Pas de session HTTP. L'etat temporaire passe par
                              Redis avec TTL.
  Deploiement mono-machine  : Localhost uniquement, pas de Kubernetes.
  Pas d'IdP externe         : L'auth est geree en interne, pas de Keycloak/Auth0.


2.3 Strategie de solution
---------------------------

Les decisions principales sont resumees dans le tableau ci-dessous. Chacune est
detaillee dans son ADR correspondant (section 2.5).

  Decoupe en services  : 3 bounded contexts DDD. Isolation des domaines,
                         scalabilite ciblee (ADR-001).
  API Gateway          : KrakenD 2.7. Agregation native, zero code Java,
                         config declarative (ADR-003).
  Cache                : Redis 7. TTL natif pour MFA + idempotency sur un seul
                         conteneur (ADR-002).
  Base de donnees      : MySQL 8.4 avec 3 schemas. Isolation logique sans 3
                         instances MySQL (ADR-004).
  Erreurs              : ErrorResponse partage via module "common". Format
                         uniforme sur les 3 services (ADR-005).
  Load balancing       : Nginx (mode LB opt-in). least_conn avec failover
                         passif, config externe a KrakenD.
  Tests de charge      : k6 (smoke / load / stress). Scenarios realistes avec
                         metriques custom.

2.4.3 Vue Processus (flux d'execution)
.......................................

Chaque service suit une architecture en couches classique :
  Controller -> Service -> Repository -> DB

Les appels inter-services sont HTTP REST synchrones via RestClient avec un
JdkClientHttpRequestFactory partage (pool de connexions TCP persistantes).

Le flow critique est UC-05 : payment-service orchestre l'operation en
appelant account-service pour le debit/credit, ecrit la transaction en base,
puis met a jour le cache Redis. L'email de confirmation est envoye de facon
asynchrone (CompletableFuture) pour ne pas bloquer la reponse HTTP.

Diagramme de sequence - UC-05 Virement (PlantUML) :
----------------------------------------------------

  @startuml CanBankX - Flux UC-05 : Virement bancaire
  actor Client
  participant "KrakenD :8080" as GW
  participant "payment-service" as PS
  participant "Redis" as Cache
  participant "account-service" as AS
  database "db_payment" as DB

  Client -> GW : POST /api/transactions\n{sourceAccount, amount, type}\nIdempotency-Key: <key>
  GW -> PS : POST /paymentservice/transactions

  PS -> Cache : GET payment:idem:<key>

  alt Cle trouvee dans Redis (doublon)
    Cache --> PS : txId existant
    PS -> DB : SELECT transaction WHERE id = txId
    DB --> PS : transaction existante
    PS --> Client : 201 (meme reponse, aucune ecriture)
  else Premiere requete
    PS -> DB : INSERT bank_transaction (PENDING)
    PS -> AS : PATCH /accountservice/accounts/number/{n}/debit
    AS -> AS : UPDATE balance = balance - amount WHERE balance >= amount
    AS --> PS : 200 OK (ou 422 si solde insuffisant)

    opt TRANSFER seulement
      PS -> AS : PATCH /accountservice/accounts/number/{n}/credit
      AS --> PS : 200 OK
    end

    PS -> DB : UPDATE bank_transaction (COMPLETED)
    PS -> Cache : SET payment:idem:<key> = txId, TTL 24h
    PS --> Client : 201 Created {id, status: COMPLETED}

    PS ->> PS : sendConfirmationEmail() [async]
  end
  @enduml

2.5 Decisions architecturales (ADR)
-------------------------------------

Les cinq decisions architecturales cles sont documentees ci-dessous.

------------------------------------------------------------
ADR-001 - Decomposition en microservices avec Bounded Contexts DDD
------------------------------------------------------------
Statut  : Accepte
Date    : 2026-01-15

Contexte :
  CanBankX doit gerer trois domaines avec des cycles de changement distincts,
  des modeles de donnees qui ne se recoupent pas, et des exigences de charge
  tres differentes. Les options evaluees etaient : monolithe modulaire,
  microservices par bounded context (option retenue), et microservices fins
  (trop granulaires).

Decision :
  Trois microservices alignes sur les bounded contexts DDD :
    identity-service  : Identite & Authentification  (port 8081)
    account-service   : Gestion des comptes          (port 8082)
    payment-service   : Paiements & Transactions     (port 8083)
  Un module "common" partage contient uniquement les contrats transverses.

Consequences positives :
  - Isolation des domaines (chaque service a son propre schema MySQL).
  - Deploiement independant.
  - Scalabilite ciblee (payment-service replique independamment).
  - Testabilite (tests de charge k6 confirment isolation : identity-service
    tient a 200 VUs meme quand payment-service est sature).

Consequences negatives :
  - Appels inter-services synchrones : panne de account-service bloque payment-service.
  - Consistance eventuelle : pas de transaction distribuee. Compensation manuelle.
  - Complexite operationnelle : API Gateway necessaire, Compose plus complexe.

------------------------------------------------------------
ADR-002 - Redis pour double usage : Idempotence et tokens MFA
------------------------------------------------------------
Statut  : Accepte
Date    : 2026-01-20

Contexte :
  Deux problemes distincts necessitaient un stockage temporaire avec expiration
  automatique. Options evaluees pour l'idempotence : base de donnees uniquement
  (lent, lock contention), cache Redis + fallback DB (retenu), cache en memoire
  JVM (ne fonctionne pas en multi-instances).

Decision :
  Redis est utilise pour les deux cas d'usage avec des TTL distincts :
    Challenge MFA       : mfa:challenge:{token}   TTL 5 minutes
    Idempotence paiement: payment:idem:{key}       TTL 24 heures

  Strategie double filet :
    1. Verification Redis (rapide, ~1 ms)
    2. Fallback sur MySQL findByIdempotencyKey si Redis est vide

Consequences positives :
  - Performance mesuree : 9 603 cache hits sur 4 minutes a 50 VUs.
  - Expiration automatique des tokens MFA.
  - Resistance aux redemarrages (fallback DB).
  - Un seul conteneur Redis pour les deux services.

Consequences negatives :
  - Redis est un SPOF : panne degrade les deux services. Mitigation : fallback DB.
  - Fenetre de race condition entre verification Redis et insertion DB.
    Gere par contrainte UNIQUE sur idempotencyKey en base.

------------------------------------------------------------
ADR-003 - KrakenD comme API Gateway (vs Spring Cloud Gateway)
------------------------------------------------------------
Statut  : Accepte
Date    : 2026-01-22

Contexte :
  Un API Gateway est requis pour un point d'entree unique, le routage vers les
  services, l'agregation de reponses et le filtrage d'en-tetes. Options :
  Spring Cloud Gateway (code Java), KrakenD (Go, config JSON declarative),
  NGINX (pas d'agregation), Kong (trop complexe).

Decision :
  KrakenD 2.7 avec configuration entierement declarative dans krakend/krakend.json.

  Routage :
    Client -> KrakenD :8080 -> /api/{resource}
      -> identity-service :8081 /identityservice/...
      -> account-service  :8082 /accountservice/...
      -> payment-service  :8083 /paymentservice/...

  Agregation : /api/accounts/{id}/summary fusionne en parallele les reponses
  de account-service et payment-service.

  Load balancing : plusieurs "host" par backend dans la config JSON.

Consequences positives :
  - Aucun code applicatif dans le gateway.
  - Agregation native triviale.
  - Performance : surcharge < 2 ms en steady-state a 50 VUs.
  - Round-robin sans configuration supplementaire.

Consequences negatives :
  - Logiques complexes (JWT) necessitent un plugin.
  - Pas de circuit breaker natif dans cette configuration.
  - Observabilite limitee du gateway (metriques cote services uniquement).

------------------------------------------------------------
ADR-004 - Schemas MySQL isoles par service (vs bases distinctes)
------------------------------------------------------------
Statut  : Accepte
Date    : 2026-01-25

Contexte :
  Options : une base MySQL par service (3 conteneurs), un seul MySQL avec un
  schema par service (retenu), base partagee (antipatterne - a eviter).

Decision :
  Un seul conteneur MySQL 8.4, trois schemas isoles :
    identity-service -> db_identity  (tables : clients)
    account-service  -> db_account   (tables : accounts)
    payment-service  -> db_payment   (tables : bank_transactions, audit_log)

  L'utilisateur applicatif "projet" recoit GRANT ALL uniquement sur son schema.
  Les JOINs cross-schemas sont interdits architecturalement.
  Le script db-init/init.sql applique les grants de facon idempotente.

Consequences positives :
  - Isolation logique (contrainte au niveau des grants MySQL).
  - Un seul conteneur a monitorer et maintenir.
  - Faible surcharge reseau.
  - DDL gere par JPA (ddl-auto: update) pour un demarrage rapide.

Consequences negatives :
  - SPOF base de donnees.
  - ddl-auto: update non idempotent en production (Flyway requis en prod).
  - Contention sous forte charge a 200 VUs (meme compte). Solution : mode LB
    avec 2 instances de payment-service.

------------------------------------------------------------
ADR-005 - Gestion des erreurs normalisee et versionnage
------------------------------------------------------------
Statut  : Accepte
Date    : 2026-02-01

Contexte :
  Sans convention, chaque service pouvait retourner ses erreurs dans un format
  different. Pour le versionnage : prefixe /v1/, header Accept-Version,
  ou prefixe par service dans le chemin (retenu).

Decision :
  Objet ErrorResponse partage via le module "common" :
    {
      "status": 422,
      "error": "Unprocessable Entity",
      "message": "Insufficient funds on account 1596875651",
      "timestamp": "2026-03-08T14:23:10.452Z"
    }

  Mapping exceptions -> codes HTTP :
    MethodArgumentNotValidException         -> 400
    ClientNotFoundException / AccountNotFoundException / PaymentNotFoundException -> 404
    BadCredentialsException                 -> 401
    Doublon email / NAS                     -> 409
    InsufficientFundsException              -> 422
    Exception non geree                     -> 500

  Versionnage : prefixe de service dans le chemin (/identityservice/**, etc.).
  KrakenD expose sous /api/** sans le prefixe interne.

Consequences positives :
  - Format d'erreur previsible. 7 cas valides par le smoke test.
  - Module "common" force la coherence.
  - Prefixe facilite le filtrage dans les logs et Prometheus.

Consequences negatives :
  - Pas de versionnage /v1/ explicite dans les URLs exposees.
  - GlobalExceptionHandler masque les stack traces (regarder les logs du service).

3.1 Schema de base de donnees
-------------------------------

Initialisation via db-init/init.sql (execute automatiquement au premier
demarrage du conteneur MySQL, puis reeexecute par le service db-init a chaque
compose up pour s'assurer que les grants sont toujours appliques).

  -- db-init/init.sql
  CREATE DATABASE IF NOT EXISTS db_identity CHARACTER SET utf8mb4;
  CREATE DATABASE IF NOT EXISTS db_account  CHARACTER SET utf8mb4;
  CREATE DATABASE IF NOT EXISTS db_payment  CHARACTER SET utf8mb4;

  CREATE USER IF NOT EXISTS 'projet'@'%' IDENTIFIED BY 'projet';
  ALTER USER  'projet'@'%' IDENTIFIED BY 'projet';

  GRANT ALL PRIVILEGES ON db_identity.* TO 'projet'@'%';
  GRANT ALL PRIVILEGES ON db_account.*  TO 'projet'@'%';
  GRANT ALL PRIVILEGES ON db_payment.*  TO 'projet'@'%';
  FLUSH PRIVILEGES;

Les tables sont creees et mises a jour automatiquement par JPA (ddl-auto: update)
au demarrage de chaque service.

Schema db_identity :
  Table clients
    id            VARCHAR(36) PRIMARY KEY
    first_name    VARCHAR(100) NOT NULL
    last_name     VARCHAR(100) NOT NULL
    email         VARCHAR(255) NOT NULL UNIQUE
    password_hash VARCHAR(255) NOT NULL
    nas           VARCHAR(9)   NOT NULL UNIQUE
    phone_number  VARCHAR(20)
    address       TEXT
    status        ENUM('PENDING','ACTIVE','SUSPENDED') NOT NULL DEFAULT 'PENDING'
    created_at    DATETIME NOT NULL

Schema db_account :
  Table accounts
    id             VARCHAR(36)    PRIMARY KEY
    account_number VARCHAR(20)    NOT NULL UNIQUE
    client_id      VARCHAR(36)    NOT NULL  (ref identity sans FK cross-schema)
    type           ENUM('CHECKING','SAVINGS') NOT NULL
    balance        DECIMAL(15,2)  NOT NULL DEFAULT 0.00
    created_at     DATETIME       NOT NULL

Schema db_payment :
  Table bank_transactions
    id                   VARCHAR(36)   PRIMARY KEY
    idempotency_key      VARCHAR(255)  NOT NULL UNIQUE
    source_account_number VARCHAR(20)  NOT NULL
    target_account_number VARCHAR(20)
    amount               DECIMAL(15,2) NOT NULL
    type                 ENUM('DEBIT','CREDIT','TRANSFER') NOT NULL
    status               ENUM('PENDING','COMPLETED','FAILED') NOT NULL
    created_at           DATETIME NOT NULL

  Table audit_log
    id              VARCHAR(36) PRIMARY KEY
    transaction_id  VARCHAR(36) NOT NULL
    action          VARCHAR(100) NOT NULL
    details         TEXT
    created_at      DATETIME NOT NULL


3.2 Isolation des schemas par service
---------------------------------------

Chaque service Spring Boot est configure avec son propre datasource pointant
exclusivement vers son schema. L'utilisateur MySQL "projet" ne peut acceder
qu'a son propre schema. Les JOINs inter-schemas sont impossibles.

  identity-service : spring.datasource.url = jdbc:mysql://mysql:3306/db_identity
  account-service  : spring.datasource.url = jdbc:mysql://mysql:3306/db_account
  payment-service  : spring.datasource.url = jdbc:mysql://mysql:3306/db_payment


3.3 Idempotence des paiements (exactly-once)
----------------------------------------------

Le mecanisme repose sur deux couches de protection :

  Couche 1 - Redis (rapide, ~1 ms)
    Cle    : payment:idem:{idempotencyKey}
    Valeur : UUID de la transaction existante
    TTL    : 24 heures
    Action : si hit -> retourner la meme reponse sans ecriture DB

  Couche 2 - Contrainte UNIQUE MySQL (filet de securite)
    Si Redis est vide (apres un restart), la requete
    findByIdempotencyKey en DB garantit qu'un doublon sera detecte
    avant l'insertion. Si deux threads tentent une insertion simultanee,
    la contrainte UNIQUE rejette le second au niveau SQL.

En cas de panne partielle sur un TRANSFER :
  - Si le debit reussit mais que le credit echoue, payment-service
    emet automatiquement un CREDIT de compensation vers le compte source.
  - La transaction passe a FAILED.
  - L'AuditLog trace chaque etape (DEBIT_ATTEMPT, DEBIT_SUCCESS,
    CREDIT_ATTEMPT, CREDIT_FAILED, COMPENSATION_DEBIT_SUCCESS, etc.).


3.4 Journal d'audit append-only
---------------------------------

La table audit_log est strictement append-only :
  - Aucune mise a jour (pas de methode update dans AuditLogRepository).
  - Aucune suppression (pas de methode delete).
  - Chaque etape d'une transaction insere une nouvelle ligne.
  - Les enregistrements sont dates et references par transactionId.

Exemple d'entrees pour un TRANSFER avec compensation :
  1. action=TRANSFER_INITIATED,  details=amount=100.00 from ACC-A to ACC-B
  2. action=DEBIT_SUCCESS,        details=account=ACC-A new_balance=400.00
  3. action=CREDIT_FAILED,        details=account=ACC-B error=Account not found
  4. action=COMPENSATION_SUCCESS, details=account=ACC-A restored_balance=500.00
  5. action=TRANSFER_FAILED,      details=compensation applied

4.2 Securite
-------------

BCrypt :
  Les mots de passe sont haches avec BCrypt force 8 (~25 ms par hash). Cette
  valeur ralentit les attaques brute-force sans degrader les performances a
  50 VUs concurrents.

Spring Security (stateless) :
  Chaque service est configure avec SessionCreationPolicy.STATELESS. Il n'y a
  pas de session HTTP. Les endpoints publics (inscription, login, MFA, actuator)
  sont exclus du filtre de securite. Les endpoints admin sont proteges.

CORS :
  CORS est active sur les trois services via @CrossOrigin ou la configuration
  Spring Security. Les origines autorisees incluent localhost:5173 (frontend).

Reseau isole :
  Les services communiquent entre eux sur le reseau Docker bridge interne
  (log430_projet-network), inaccessible depuis l'exterieur. Seuls KrakenD
  (:8080), le frontend (:5173), Grafana (:3000) et Prometheus (:9090) sont
  exposes sur la machine hote.


4.3 Gestion des erreurs normalisee
------------------------------------

Toutes les exceptions passent par le GlobalExceptionHandler dans le module
"common". Toutes les reponses d'erreur suivent le meme format :

  {
    "status": <code HTTP>,
    "error": "<libelle HTTP>",
    "message": "<message explicite>",
    "timestamp": "<ISO-8601>"
  }

Exemples :
  POST /api/transactions avec solde insuffisant :
    HTTP 422 - {"status": 422, "error": "Unprocessable Entity",
                "message": "Insufficient funds on account 1596875651", ...}

  POST /api/clients avec email deja utilise :
    HTTP 409 - {"status": 409, "error": "Conflict",
                "message": "Email already in use: test@canbankx.ca", ...}

  POST /api/auth/login avec mauvais mot de passe :
    HTTP 401 - {"status": 401, "error": "Unauthorized",
                "message": "Bad credentials", ...}

7 cas d'erreur valides par le smoke test k6 :
  - 400 (champs manquants)
  - 401 (mauvais credentials)
  - 404 (ressource inexistante)
  - 409 (doublon email/NAS)
  - 422 (solde insuffisant)
  - 422 (idempotency - meme reponse retournee)
  - 404 (compte inexistant pour la transaction)

5.1 4 Golden Signals (Prometheus + Grafana)

L'observabilite est basee sur les 4 Golden Signals de Google SRE. Chaque service

  Metrique : histogram_quantile(0.95, rate(http_server_requests_seconds_bucket[1m]))

  Metrique : rate(http_server_requests_seconds_count{status=~"5.."}[1m])

  Metriques :
    jvm_memory_used_bytes / jvm_memory_max_bytes   (heap JVM)

5.5 Load balancing Nginx (N=1 vs N=2 instances)
-------------------------------------------------

Configuration Nginx (nginx/nginx-all.conf) :
  Algorithme : least_conn (connexion la moins chargee en premier)
  Failover passif : max_fails=3, fail_timeout=10s
  Keepalive : 16 connexions persistantes vers identity/account, 32 vers payment
  proxy_next_upstream : retry automatique en cas d'erreur 502/503/504

Demarrage mode LB :
  KRAKEND_CONFIG=krakend.json docker compose --profile lb up -d

Comparaison N=1 vs N=2 instances (load test 50 VUs) :

  Metrique                      N=1 (direct)   N=2 (nginx-lb)
  Load test tx p95 (50 VUs)     60 ms          [A MESURER]
  Load test erreurs (50 VUs)    0%             [A MESURER]
  Stress test tx success (200 VUs) voir ci-dessus [A MESURER]
  Point de rupture estime       ~100-150 VUs   ~200-300 VUs

Hypothese : doubler les instances de payment-service repousse le point de
rupture car le pool HikariCP de chaque instance est independant
(50 + 50 = 100 connexions DB disponibles en N=2 vs 50 en N=1).

Test de tolerance aux pannes :
  En mode LB, tuer une instance en cours de charge :
    docker stop payment-service-2
  Nginx detecte l'echec via max_fails et redirige vers l'instance restante.
  Le parametre proxy_next_upstream permet de rejouer la requete echouee.

5.6 Cache Redis - gains mesures
---------------------------------

Redis est utilise pour deux usages avec des TTL distincts.

Tokens MFA (identity-service) :
  Cle    : mfa:challenge:{token}
  TTL    : 5 minutes
  Gain   : Expiration automatique, aucune tache planifiee necessaire.
           Aucun SELECT periodique en base pour nettoyer les tokens expires.

Idempotence paiements (payment-service) :
  Cle    : payment:idem:{idempotencyKey}
  TTL    : 24 heures
  Gain   : 9 709 cache hits en 4 minutes de load test a 50 VUs.
           Chaque hit evite : 1 SELECT DB + 1 INSERT DB + 2 appels inter-services.

Risque de donnees perimees (stale data) :
  Les tokens MFA en cours sont perdus si Redis redemarre. L'utilisateur
  devra recommencer le processus de login. Impact acceptable.
  Les cles d'idempotency tombent en fallback sur la DB (double filet).

Configuration Redis (docker-compose.yaml) :
  maxmemory         : 256 MB
  maxmemory-policy  : volatile-lru (expulse les cles avec TTL les moins utilisees)
  appendonly        : yes (persistance sur disque en cas de restart)

SECTION 6 - API GATEWAY (KrakenD)
================================================================================

6.1 Configuration et routage
------------------------------

KrakenD 2.7 est configure entierement via un fichier JSON declaratif.
Deux configurations existent :
  krakend-nolb.json : Mode direct (defaut, 1 instance par service)
  krakend.json      : Mode LB (via nginx-lb, --profile lb)

Point d'entree unique : http://localhost:8080

Routage par prefixe :
  /api/clients/**     -> identity-service :8081 /identityservice/...
  /api/auth/**        -> identity-service :8081 /identityservice/auth/...
  /api/accounts/**    -> account-service  :8082 /accountservice/...
  /api/transactions/**-> payment-service  :8083 /paymentservice/...

Filtrage des headers :
  Content-Type, Authorization : transmis vers tous les services
  Idempotency-Key : transmis uniquement vers payment-service
  Headers non listes : bloques par KrakenD (securite par defaut)

Timeout global : 15 secondes
Cache TTL global : 300 secondes (utilise pour les endpoints GET si configure)
Health check : GET /__health (utilise par le healthcheck Docker Compose)


6.2 Agregation de reponses - Endpoint summary
----------------------------------------------

L'endpoint /api/accounts/{id}/summary est un exemple d'agregation native
KrakenD. Il fusionne en parallele deux reponses en une seule.

Configuration (extrait krakend.json) :
  {
    "endpoint": "/api/accounts/{id}/summary",
    "method": "GET",
    "output_encoding": "json",
    "backend": [
      {
        "url_pattern": "/accountservice/accounts/number/{id}",
        "method": "GET",
        "host": ["http://nginx-lb:8082"],
        "group": "account"
      },
      {
        "url_pattern": "/paymentservice/transactions/account/{id}/recent",
        "method": "GET",
        "host": ["http://nginx-lb:8083"],
        "is_collection": true,
        "group": "recentTransactions"
      }
    ]
  }

Reponse aggregee retournee au client :
  {
    "account": {
      "id": "...",
      "accountNumber": "ACC-1234",
      "type": "CHECKING",
      "balance": 450.00
    },
    "recentTransactions": [
      {"id": "...", "amount": 50.00, "type": "DEBIT", "status": "COMPLETED"},
      ...
    ]
  }

Sans KrakenD, le client aurait du faire deux requetes sequentielles et les
fusionner lui-meme. L'agregation reduit la latence percue et simplifie le client.


6.3 Comparaison Direct vs API Gateway
---------------------------------------

Toutes les requetes k6 passent par KrakenD. La surcharge introduite par le
gateway a ete mesuree comme negligeable.

Resultats mesures (50 VUs, load test) :
  Via KrakenD (lectures)     : mediane 4 ms, p95 17 ms
  Via KrakenD (transactions) : mediane 13 ms, p95 60 ms

La surcharge de KrakenD est incluse dans ces chiffres car toutes les requetes
passent deja par la gateway. Des tests directs (sans KrakenD, via les ports
internes des services) n'ont pas montre de difference significative pour les
endpoints simples. L'overhead reel de KrakenD est estime a < 2 ms en
steady-state.

Valeur ajoutee de KrakenD (au-dela de la performance brute) :
  - Point d'entree unique : le client ne connait pas les ports internes.
  - Agregation /summary : 1 requete client pour 2 backends en parallele.
  - Filtrage des headers : les services internes recoivent uniquement ce
    dont ils ont besoin.
  - Config declarative dans krakend.json : aucun code Java a maintenir.
  - Facilite le load balancing en mode nginx-lb (transparent pour KrakenD).

7.2 Dockerfiles multi-stage
-----------------------------

Chaque service utilise un Dockerfile multi-stage pour reduire la taille de
l'image finale et separer la phase de build de la phase d'execution.

Exemple pour payment-service (Dockerfile) :
  Stage 1 - Build (maven:3.9-eclipse-temurin-21) :
    - Copie pom.xml et sources
    - mvn package -DskipTests
    - Produit le JAR dans target/

  Stage 2 - Runtime (eclipse-temurin:21-jre-alpine) :
    - Copie uniquement le JAR depuis stage 1
    - EXPOSE 8083
    - ENTRYPOINT ["java", "-jar", "/app.jar"]
    - Aucun SDK, aucun source dans l'image finale (~150 MB vs ~500 MB)


7.3 Variables d'environnement
------------------------------

Les secrets et la configuration sont passes via des variables d'environnement
(fichier .env ou variables shell, jamais hard-codes dans les images) :

  DB_USER           : utilisateur MySQL applicatif (defaut: projet)
  DB_PASSWORD       : mot de passe MySQL applicatif
  DB_ROOT_PASSWORD  : mot de passe root MySQL
  DB_PORT           : port expose de MySQL (defaut: 3306)
  REDIS_PORT        : port expose de Redis (defaut: 6379)
  KRAKEND_CONFIG    : fichier de config KrakenD (defaut: krakend-nolb.json)

En mode LB, les services repliques (payment-service-2) pointent leurs
appels inter-services vers nginx-lb plutot que directement vers les services.
Cela assure que les repliques distribuent aussi le trafic interne.

8.3 Risques et dette technique
--------------------------------

Risque 1 : SPOF base de donnees
  Severite : Haute
  Description : La panne de l'unique instance MySQL affecte les 3 services.
  Mitigation en place : Volumes Docker persistants (donnees survivent au restart).
  Solution production : MySQL Group Replication ou RDS Multi-AZ.

Risque 2 : ddl-auto: update en production
  Severite : Moyenne
  Description : JPA applique les changements de schema automatiquement.
                Non idempotent, peut causer des pertes de donnees en prod.
  Mitigation en place : Acceptable pour un contexte academique.
  Solution production : Migrer vers Flyway ou Liquibase.

Risque 3 : Pas de JWT reel
  Severite : Moyenne
  Description : L'authentification est basique (challenge token dans Redis).
                Pas de token JWT signe dans les headers pour les appels inter-services.
  Mitigation en place : Reseau Docker isole + BCrypt pour les mots de passe.
  Solution production : Integrer Keycloak ou generer des JWT signes RS256.

Risque 4 : Pas de circuit breaker
  Severite : Moyenne
  Description : Si account-service est lent, payment-service est bloque
                jusqu'au timeout de 15 secondes de KrakenD.
  Mitigation en place : Timeout KrakenD 15 s.
  Solution production : Resilience4j avec circuit breaker sur les clients REST.

Risque 5 : Contention DB sous forte charge
  Severite : Haute (observee a 200 VUs, 1 compte partage)
  Description : Tous les VUs sur le meme compte -> deadlocks InnoDB.
  Mitigation en place : 20 comptes isoles (1 par groupe de VUs) dans stress-test.js.
                        Mode LB avec 2 instances de payment-service.
  Solution production : Read replica MySQL pour les lectures. Sharding par compte.

Risque 6 : SPOF Redis
  Severite : Faible
  Description : Si Redis tombe, MFA ne fonctionne plus et l'idempotence
                depend uniquement de la DB (plus lent).
  Mitigation en place : Fallback DB sur l'idempotency.
  Solution production : Redis Sentinel ou Redis Cluster.
